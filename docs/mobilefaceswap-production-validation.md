# MobileFaceSwap 운영 경로 검증 (2026-10-19~20)

`feat/mobilefaceswap-runtime/#66`의 메인 gRPC 경로와 RTX 3090에서 검사했다.
비교 기준은 기존 배포 `430b6a4`에 최신 main `7bf78f9`의 blur 수정을 병합한 `20aa425`이다.
새 이미지 변경에 따른 영향과 코드 최적화 효과를 구분하기 위해 성능 비교는 같은 기존
프리셋·입력으로 실행하고, 새 프리셋은 별도로 전수 캐시 생성과 합성 검사를 수행했다.

## 보존한 계약과 변경한 처리

- `protos/ai_processor.proto`는 `7bf78f9`와 byte-identical이며 SHA-256은 `a55690094906062a294cc1bb1ecfde971f434b8d18f9115eed22f44b1c14207e`이다.
- 기본 backend는 InSwapper, 기본 요청 모드는 blur이다. MobileFaceSwap는 AI 서버 CLI로 선택하며 Go 요청에 새 필드를 추가하지 않는다.
- metadata의 30프레임 갱신, stream별 identity, whitelist, held face와 번호판 blur, 실패 시 원본 미출력 계약을 유지한다.
- MobileFaceSwap는 얼굴별 전체 프레임 복사를 제거하고 검증을 마친 ROI만 caller 소유 출력에 반영한다. 입력 crop은 항상 원본 프레임에서 읽는다.
- 서로 다른 인물은 조건부 가중치가 달라 합성 forward를 각각 실행한다. CUDA 입출력 전송은 최대 8개씩 묶고 동기화를 줄인다. 같은 CUDA Graph의 출력은 재실행 전에 별도 buffer에 복사한다. 이를 서로 다른 가중치의 단일 forward batch로 해석하면 안 된다.
- CUDA launcher는 준비된 가중치를 요구하고 40개 기본 표정 source를 시작 시 예열한다. GPU source cache는 64개이며 1..128 범위로 설정한다. 캐시 준비를 생략한 배포는 시작을 거부하고, 요청 중 cache 오류는 해당 얼굴의 blur로 처리한다.

## 품질과 클라이언트 검사

- 기존 프리셋: 1/2/4/8명 × 6각도 × 480p/FHD, 총 48개 입력에서 serial/grouped 최종 RGB가 bitwise 일치했다. polygon 밖 픽셀도 원본과 동일했다. FHD는 parity 검증이며 브라우저 FHD 처리량 검증이 아니다.
- 새 프리셋: 560개 source 전부 원본 ONNX landmark·Paddle conditioning·저장 후 재로드를 검증했다. 캐시 준비는 4 CPU worker에서 126.9초였다. 24개 다중 얼굴 입력에서도 serial/grouped 출력과 얼굴 밖 픽셀이 일치했다.
- 저장된 실제 합성 이미지에서 얼굴 위치, 눈·입과 피부 경계, 배경 유지 상태를 검토했다. 합성 모델 자체의 부드러워지는 피부 질감은 남으며, 측면·심한 가림·실제 카메라의 장시간 품질을 보장하는 검사는 아니다.
- Go gRPC 클라이언트를 현재와 동일한 proto로 빌드해 3090에 연결했다. blur/face_swap/face_metadata 각각 JPEG 35프레임, frame ID·timestamp echo, 합성 35/35, metadata-only 빈 data, stream 중 모드 변경의 INVALID_ARGUMENT를 확인했다. 새 프리셋 적용 환경에서도 같은 검사를 통과했다. 실제 Go 백엔드 전체 서비스와의 배포 E2E는 포함하지 않는다.
- Mac 전체 Python 테스트 337개(가속기 전용 5개 제외), Linux/3090 337개(NVENC opt-in 1개 제외)를 통과했다. NVENC를 켠 별도 WebRTC 테스트 14개도 모두 통과했다. JavaScript 2개, 협업 정책 29개, 변경 범위 Ruff·format·shell 문법·diff 검사를 통과했다.

## 긴 프레임과 freeze 원인 추적 (2026-10-20)

동일 640×480·4얼굴 Y4M을 사용하고, 운영과 같은 설정의 별도 8444/50062 서버에서
시험을 순차 실행했다. Python GC callback과 프로세스 정지 감시를 임시로 붙였으며,
운영 코드에는 단계별 timing·media timestamp·게이트웨이 monotonic 시각만 추가했다.

- 수정 전 120초: 서버 최대 153.93ms인 프레임의 serialize가 137.58ms였고, 같은 시각 AI 프로세스의 generation-2 GC가 136.05ms 동안 실행됐다. 수거한 객체는 0개였다. 검출 4.60ms·합성 10.55ms는 정상이었다.
- 수정: 모델 예열 후 스트림 수락 전에 `gc.collect()`와 `gc.freeze()`를 실행한다. 준비된 framework·모델 객체를 반복해서 전체 검사하지 않고, 새 세션 객체의 자동 GC는 계속 유지한다. 종료 시 freeze를 해제한다.
- CUDA 메모리 검사: source cache 상한 2로 8개 프리셋을 교체했고, 이전 모델 weak reference 해제와 일정한 PyTorch 할당량을 확인했다. 강제 전체 GC 50.16~61.45ms가 freeze 후 0.08~0.27ms로 감소했다. 새 순환 참조 수거·기존 freeze 소유권·종료 복원도 별도 subprocess 테스트로 통과했다.
- 별도의 freeze: 수정 전 추적 시험에서 연속 seq 1541→1542의 게이트웨이 생성 간격은 30.95ms, 브라우저 수신 간격은 275.90ms였다. 두 프레임 AI 처리는 17.48/17.47ms였다. 서버의 긴 추론으로 설명되지 않는 전송 구간 지연이며, 같은 구간 Chrome freeze 0.225초와 RTP 손실 증가가 관찰됐다.
- 같은 Mac↔GPU의 무부하 ping 100회는 손실 0%, RTT 최소/평균/최대 20.35/58.92/180.43ms였다. 회선 지연과 서버 정지는 별도로 평가한다.

외부 회선을 제외한 RTX 3090 내부 Chrome에서도 같은 페이지·NVENC·Y4M을 사용했다.
120초 동안 29.67 FPS, 표시 지연 p50/p95 33.3/33.6ms, 서버 p95/최대 19.30/24.16ms,
freeze 0회·100ms 초과 표시 간격 0회·RTP 손실 0개였다. 3569개 telemetry 모두 4얼굴
swapped였다. 이는 서버 내부 경로 검증이며 Mac까지의 네트워크 성능 수치가 아니다.

수정 후 Mac→8444 180초 시험은 26.06 FPS, 표시 지연 p50/p95 183.3/215.5ms,
서버 p95/최대 19.08/23.72ms였다. freeze는 4회·총 1.336초로 남았다. 가장 긴 구간은
서버 생성 간격 31.73ms에 브라우저 수신 간격 651.30ms였으며, 원본 미리보기는 계속
진행했다. 서버 GC 수정만으로 이 회선의 freeze가 해결됐다고 해석하지 않는다.
공유기까지 직접 ping도 3.12/21.89/117.44ms(최소/평균/최대, 100회)로 흔들려
지연이 외부 서버 이전의 Mac 무선 구간에서도 나타났다.

운영 8443에 `40874a2`를 적용한 뒤 사용자 승인하에 Mac AWDL을 120초간 끄고
자동 원복했다. 1초 간격 모니터의 110개 표본 모두 비활성 상태였다. 그 안의 100초
영상 측정은 27.54 FPS, 표시 지연 p50/p95 134.2/183.3ms, 서버 p95/최대
19.21/22.81ms, freeze 0회·100ms 초과 간격 15회·손실 0개였다.
2928개 telemetry 모두 4얼굴 swapped였다. 같은 구간 100회 ping의 평균/최대는
공유기 13.05/91.56ms, GPU 39.27/127.22ms로 감소했다. 무선 경로 변동이 여전히
남고 시간대를 바꾼 비교이므로 AWDL을 유일한 원인으로 확정하거나 영구 비활성화하지 않았다.

AWDL 원복 후 운영 8443을 같은 입력으로 120초 재검증했다. 26.23 FPS,
표시 지연 p50/p95 167.3/233.4ms, 서버 p95/최대 19.19/23.45ms,
freeze 1회·0.375초, 100ms 초과 간격 34회, 손실 4개였다. 3280개 telemetry 모두
4얼굴 swapped였다. freeze 구간의 연속 결과 생성 간격은 20.40ms, 수신 간격은
425.60ms였다. **서버 GC 긴 프레임은 수정했지만 현재 Mac 무선 연결의 freeze는 남아
있으므로 PR의 전체 해소 항목은 미완료로 유지한다.** AWDL만의 인과관계를 확정하지
않았고 영구 설정 변경도 하지 않았다. 안정적인 유선 경로 등으로 외부 전송 구간을 바꾼
재검증이 필요하며, 더 큰 재생 buffer로 숨기면 표시 지연이 증가하는 trade-off가 있다.

최종 운영은 `40874a2`, `0.0.0.0:8443`, NVENC, active peers 0, NRestarts 0이다.
임시 8444/50062 서비스는 종료했다. 물리 카메라·다른 회선·더 긴 다중 사용자 시험까지
보장하는 결과가 아니다. 원시 결과는 로컬 `reports/freeze-66/{before,traced,loopback,
after,awdl-off,restored}`와 GC 감사·회귀 로그에 보관했다.

후속 회귀 검증은 Mac 전체 340개(가속기 전용 5개 제외), Linux 전체 340개
(명시적 artifact/NVENC 옵션이 필요한 2개 제외)를 통과했다. 제외된 경로는 실제
SCRFD engine을 지정한 cache/CUDA 테스트 9개와 NVENC 테스트 14개로 별도 통과했다.
JavaScript 2개·협업 정책 29개·변경 범위 Ruff/format/diff 검사와 기존 proto 동일성도
확인했다. 모델·입출력 픽셀 처리·Go 요청 계약은 이번 GC/진단 수정에서 변경하지 않았다.

## 전송 freeze 추가 분리 검증 (2026-10-20)

같은 Mac·학교 Wi-Fi와 640×480·4얼굴·30 FPS 입력을 유지했다. 기본 경로는
Tailscale이며 직접 UDP 조건에서만 VPN을 우회했다. AWDL은 활성 상태로
유지했으며, 아래 영상 시험은 서로 겹치지 않게 실행했다.
표시 지연은 로컬 미리보기에서 반환 영상 표시까지의 시간이다.

| 조건 | 시간 | 표시 FPS | 지연 p50 / p95 | 서버 최대 | Chrome freeze |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 전송, 별도 8444 | 120초 | 26.36 | 166.7 / 183.9ms | 24.37ms | 0회 |
| 패킷 전송 분산 실험, 별도 8444 | 180초 | 26.21 | 166.5 / 183.4ms | 23.65ms | 1회, 0.211초 |
| 기존 전송, 운영 8443 | 180초 | 26.61 | 166.7 / 183.9ms | 23.62ms | 1회, 0.201초 |
| Tailscale 우회 직접 UDP, 별도 8444 | 120초 | 26.09 | 200.1 / 250.6ms | 23.34ms | 1회, 0.194초 |

기존 전송은 최대 50개 RTP 패킷을 한 프레임에서 보냈으며 전송 구간 최대는
1.12ms였다. 별도 진단 프로세스에서 영상·비트레이트를 유지하고 전송을
16ms 이내에 분산하도록 계획했으나 FPS·지연 개선과 freeze 해소를 확인하지 못했다.
이 실험 코드는 운영 경로와 Git 변경에 포함하지 않았다.

영상과 독립된 UDP echo를 같은 Mac↔3090 경로에 50ms 간격으로 함께 보냈다.
패킷 전송 분산 시험의 216.5ms 표시 공백에서 UDP 응답 4개도 지연 후 함께
도착했고 최대 RTT는 231.84ms였다. 게이트웨이 연속 결과 생성 간격은 26.5ms,
브라우저 통계 수신 간격은 248.9ms였다. 영상 시험과 겹치는 140초 동안 보낸
독립 UDP 2,800개는 모두 수신했다.

운영 시험에서도 약 199.4ms 표시 공백과 독립 UDP RTT 258.40ms가 겹쳤다.
영상 전후를 포함한 210초 동안 보낸 4,200개 UDP 응답은 모두 수신했고
RTT p50/p95는 29.07/109.53ms였다.
같은 공백 근처 공유기 ping 표본은 4.45~32.19ms였으므로 이 사건을 학교 Wi-Fi
단독 원인으로 확정하지 않는다. 영상 처리 외의 Tailscale·무선·외부 회선이 포함된
전송 경로에서도 지연이 발생한다는 근거이며, GPU 추론 시간과 구분한다.

별도 8444 게이트웨이에서 VPN 후보를 제외하고 공개 STUN의 후보로 직접 UDP를
연결했다. 시험 브라우저는 준비된 후보로 협상하도록 대기 방식을 임시 조정했다.
실제 선택된 ICE 후보 양쪽 모두 공개 IPv4의 `srflx`·UDP였고, Mac 쪽 networkType은
`wifi`였다. HTTP 제어 연결은 기존 Tailscale URL을 사용했지만 영상은 VPN을 우회했다.
이 조건에서도 freeze가 재현돼 Tailscale만의 문제로 단정하지 않는다. 지연도 증가해
직접 연결과 임시 협상 설정은 운영에 반영하지 않았다.
운영 4,905개·직접 연결 3,236개 frame telemetry 모두 4얼굴 swapped였으며
blur fallback은 없었다. 모델과 프리셋, 기본 모드, 기존 Go protobuf는 유지했다.

마지막으로 운영 8443에 3090 내부 Chrome을 연결해 외부 회선을 제외하고 180초
재검증했다. 서버 p95/최대는 19.62/23.58ms, 표시 지연 p50/p95는 33.4/66.8ms,
freeze와 RTP 손실은 모두 0이었다. 5,374개 응답 모두 4얼굴 swapped였다.
Chrome은 5,373개를 디코딩했고 `framesDropped`는 0이었다. 이때 디코딩 처리율은
29.85 FPS였지만 화면의 frame ID로 추적한 표시 FPS는 25.82였다. 100ms 초과
표시 간격은 3회, 최대 100.3ms였다. 디코딩 수치를 화면 FPS로 대체하거나
앞선 내부 시험의 29.67 FPS가 항상 유지된다고 해석하지 않는다.

이 결과는 외부 전송 freeze를 해소했다는 의미가 아니다. 앞선 전체 해소 보류 이후
서버 처리 정지 해소와 전송 원인 분리 검증을 머지 판단 범위로 정리하며, 현재
회선에서의 간헐적 freeze와 다중 얼굴·세션의 처리량 한계는 계속 공개한다.
원시 측정은 로컬 `reports/freeze-72/`에 보관했다.

## 프리셋 배포

`config/face_presets.json`은 `natural_faces_v2` 560장의 새 SHA-256을 참조한다.
이미지와 모델, 생성된 가중치·engine, 인증서·측정 원본은 Git에 포함하지 않는다.
배포 시 새 `dataset_manifest.csv`와 `images/`가 포함된 배포본을 함께 설치해야 한다.
기존 560장과 카탈로그는 Mac의 `~/Downloads/innolive-face-presets-backup-20261019-231541`
아래 보존했고 모든 파일 해시를 대조했다. `best.pt`도 변경하지 않았다.

3090에서도 `~/Downloads/innolive-face-presets-backup-20261019-144532`에 기존 세트를
보존하고 해시를 검증했다. 새 카탈로그 SHA-256은
`799e042fc40421ec70ff04f32e49bb55368203d0f2805cfeef8b538e0222166d`이다.
운영 코드 `a263b49`와 새 560장을 함께 배포하고 40개 기본 source 예열 후 SERVING을 확인했다.
현재 NVIDIA 커널은 `595.99.02`이며 시스템 라이브러리로 CUDA와 NVENC를 사용했다.
이전 커널용 `595.91.07` 서비스 라이브러리를 강제로 지정하면 CUDA error 803이 발생하므로
그 경로를 수동 지정하지 않는다. launcher는 실제 로드된 커널 버전에 맞는 경로만 선택한다.

새 프리셋을 사용한 별도 raw gRPC 검증은 같은 640×480·예열 4초·측정 12초 조건에서
1명 × 1세션 104.25 FPS, 8명 × 1세션 34.08 FPS, 4명 × 2세션 각 37.83~37.92 FPS였다.
모든 측정 응답에서 해당 얼굴 수 전체가 합성됐다. 프리셋과 입력이 바뀐 결과이므로
기존 프리셋의 전후 표와 직접적인 개선율로 비교하지 않는다.

기존 이미지 디렉토리가 다른 세트이면 importer는 덮어쓰기를 거부한다. 기존 세트를 백업한 후
새 배포본을 import하고, 준비된 cache와 카탈로그가 일치하는 상태에서 AI 서버를 재시작한다.
자세한 명령은 [CUDA 운영 가이드](mobilefaceswap-cuda.md)를 따른다.

## 재현 명령과 측정 한계

```bash
# 3090 내부, 다른 부하 시험과 겹치지 않게 실행
.venv/bin/python scripts/benchmark_face_capacity.py \
  --target 127.0.0.1:50062 --cases 1x1,2x1,4x1,8x1,1x4,4x2 \
  --warmup 4 --seconds 12 --output reports/capacity
.venv/bin/python scripts/benchmark_mobilefaceswap_render.py \
  --manifest config/face_presets.json --output reports/render-parity
```

측정 원본은 로컬과 3090의 `reports/mobilefaceswap-production-66` 또는 검수 디렉토리
`reports`에 보관한다. GPU 가중치 캐시·전송 묶음은 stream을 넘어서 동시에 재사용하지 않도록
기존 bounded face executor를 유지한다. 세션을 무제한 병렬 실행하면 이 메모리 소유권과
지연 상한이 깨질 수 있다. 탐지·합성·회선·브라우저 병목이 모두 없어졌다는 보장은 하지 않는다.
