# 성능 개선 프로그램: 30fps 서빙과 10클라이언트 동시 처리

- 이슈: #21 (브랜치 `feat/yolo-mask-batch/#21`, PR #24)
- 목표: 어떤 환경에서도 30fps 서빙, 10클라이언트가 안정적으로 30fps 사용
- 실측 베이스라인: `reports/issue-21-bench.md`, 원시 데이터 `reports/issue-21-bench.json`
- 측정 하네스: `experiments/trt_swap_client/bench_lab.py` (base/opt 공용)
- 운영 규칙: 서버에서 지속 실험, 의미 있는 단위로만 커밋 (막무가내 커밋 금지)

## 1. 목표 정의와 타당성 (2026-09-15 실측)

"30fps"를 두 개로 분리한다. 합쳐서 논하면 프로그램이 깨진다.

- **렌더 FPS** (클라이언트가 보는 화면 부드러움): WebRTC 경로는 이미
  `SwapVideoTrack`의 독립 클럭으로 송출한다. 스왑이 늦어져도 화면은
  30fps로 나갈 수 있다. → **달성 가능, 보장해야 할 SLO**
- **스왑 FPS** (얼굴 합성이 새로 끝나는 속도): 얼굴당 forward 13ms가
  고정비라서 1x1 기준 초당 ~25회가 천장이다.

10클라이언트 x 30fps 풀스왑 = 초당 300스왑이 필요하다.
현행 합계 처리량은 세션 수와 무관하게 **~26/s에 고착**된다 (실측):

| 부하 | 합계 fps | 세션당 fps | p50 | p95 |
| --- | --- | --- | --- | --- |
| 1세션 | 25.6 | 25.6 | 39ms | 40ms |
| 4세션 | 26.2 | 6.5 | 153ms | 155ms |
| 10세션 | 25.8 | 2.6 | 314ms | 466ms |

갭은 **약 12배**다. 튜닝으로 메울 수 있는 것은 2~3배(§3)이고,
나머지는 구조로 메운다(§4). "3090 단일 장에서 10클라 풀스왑 30fps"는
물리적으로 불가하다는 것을 전제로 깐다. 프로그램의 성공 기준은
"렌더 30fps 보장 + 스왑 처리량 최대화 + 과부하에서 우아한 저하"다.

## 2. 병목 지도 (1얼굴 43ms 기준)

detector 3.2 / yunet(CPU) 10.1 / prepare 0.8 / forward(TRT) 13.0 /
paste(CPU) 11.2. 다중 얼굴은 forward가 얼굴 수에 비례한다.
파이프라인이 `GPU → CPU → GPU → CPU` 직렬이라 한쪽이 놀 때가 많다
(GPU 사용률 30~50%의 정체).

## 3. 튜닝 프로그램 (3090, 품질 게이트 유지)

게이트: 1얼굴 프레임 베이스 대비 비트 동등(또는 maxdiff ≤ 2),
ONNX FP32 대비 MAE ~1e-3, YOLO mask 내외 보존·fallback 육안 확인.

- **Phase 0 — 프로파일 (반나절)**: Nsight Systems 타임라인 +
  Polygraphy 레이어별 시간. 13ms의 행방을 확정하고 아래 순서를 고른다.
  도구 둘 다 서버에 있다 (`nsys`, polygraphy).
- **Phase 1 — 무리스크 (1~2일)**: 엔진 rebuild 튜닝
  (optimization level 최대, channel-last 허용, timing cache,
  workspace 확대) + CUDA graphs 캡처. 기대 10~30%.
- **Phase 2 — 혼합 정밀도 (3~5일)**: 레이어별 오차 측정 후 깨지는
  상위 레이어만 FP32 고정, 나머지 FP16. 기대 forward 13→7ms.
  전체 FP16 탈락 판정과 혼동하지 않는다 (리포트 4절).
- **Phase 3 — 구조 (1주)**: YuNet TRT 엔진화 (10ms → 1~2ms, 동일 모델이라
  화질 논쟁 없음), CPU/GPU 소프트웨어 파이프라이닝 (context 2개로
  forward와 paste 겹치기). 기대 1얼굴 43→25ms.

Phase 1~3 전부 성공 가정 시 1얼굴 43→18ms(2.4배), 합계 ~60/s.
그래도 300/s에는 한참 못 미친다. §4가 본 게임이다.

## 4. 구조적 대안 (동시 처리량·안정성)

튜닝으로 안 되는 영역. 각각 리서치 후 본 브랜치 범위(§5)와 맞춰 단계 도입한다.

1. **렌더/스왑 분리 보장**: 30fps 렌더를 SLO로 못 박는다.
   스왑이 늦어지면 최신 완성 프레임을 유지하고 렌더 클럭은 흔들지 않는다
   (WebRTC 경로는 이미 이 구조, WebSocket/JPEG 경로로 확대).
   과부하 지표: p95 렌더 간격, stale 프레임 비율.
2. **적응형 스왑 레이트**: 얼굴·세션별 우선순위 스케줄링.
   - 큰/가까운 얼굴은 매 프레임, 작거나 정적인 얼굴·트랙은 N프레임마다
     스왑하고 사이에는 트래커 기반 워프로 유지한다.
   - 세션당 최소 보장률 + 잔여 용량 균등 분배, 큐가 임계치를 넘으면
     구 세션부터 최신 프레임만 남기고 드롭한다 (coalescing 연장선).
   - 체감 30fps를 유지하면서 스왑 연산량을 1/2~1/4로 줄이는 게 목표.
3. **세션 격리와 과부하 차단**: 세션당 inflight 상한, 전역 admission control,
   10세션 초과분은 대기열이 아니라 명시적 busy 응답. p95 466ms 같은
   꼬리를 만들지 않는다 (느리게 전부 처리하느니 빨리 일부를 떨군다).
4. **듀얼 GPU 분할** (프로덕션 5070Ti dual이 정답인 영역):
   세션 단위 GPU 할당 + 세션당 최소율 보장. 단일 GPU 상한(약 60/s)을
   U당으로 곱한다. 3090에서 검증한 스케줄러를 그대로 이전한다.
5. **모델 전략 (중장기)**: 경량 swapper 증류·아키텍처 교체는 별도 리서치로
   분리한다. Blackwell(FP8/FP4)은 5070Ti 이전 시 재검증 항목이다(§5).

## 5. 5070Ti dual 이전 시 주의 (3090 결과가 그대로 안 감)

- 엔진은 아키텍처 종속이라 **전량 rebuild**가 필요하다
  (Blackwell sm_120은 TRT/CUDA 버전 요구가 다름).
- 정밀도 게이트(ONNX FP32 대비 MAE, mask 내외, fallback)를 이전 체크리스트로
  그대로 돌린다. 본 브랜치의 검증 스크립트(`/tmp`가 아닌 커밋된 하네스만)를 쓴다.
- FP8/FP4는 5070Ti에서 새로 열리는 선택지라 Phase 2의 연장으로 검증한다.
- 3090에서 통하는 것(스케줄러·coalescing·timing 구조)은 그대로 가고,
  숫자(FPS·지연)는 5070Ti에서 다시 잰다.
